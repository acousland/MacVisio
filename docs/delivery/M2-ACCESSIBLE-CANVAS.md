# Semantic canvas and keyboard authoring

This WP-11-T01/T02 implementation consumes the accepted M1 retained scene/runtime. It is a bounded implementation slice; real VoiceOver and a complete physical keyboard authoring journey remain separate acceptance requirements.

`CanvasAccessibility` retains AppKit accessibility elements by `(source page UUID, node-or-edge UUID)`. It reads the already prepared scene, visibility flags, paint order, group indexes, endpoint indexes and bounds. Accessibility queries perform no ShapeSheet evaluation, routing, text measurement or model mutation. Hidden layers and descendants are omitted. Background content is exposed with its own source page identity and a background label; editing actions require the active foreground page. A retained element for a removed/hidden object cannot perform a stale action.

The navigation order follows composed scene layers and each layer's prepared paint order. Groups, members, incident connectors and connector endpoints are linked accessibility objects. Connector labels identify source and destination; shapes prefer explicit Shape Data keys `AltText` or `AccessibilityDescription` (case-insensitive exact key match and trimmed nonempty value), then visible text and shape kind. Arbitrary Shape Data is never guessed to be an alternative description. The existing Shape Data editor can author those explicit values. Lock explanations remain available on selectable objects. Screen frames apply the layer's paper scale/composed-page offset, canvas zoom/origin, actual canvas-to-window conversion and window-to-screen conversion each time; scrolling and moving windows do not leave cached frames behind.

The canvas exposes a layout area and semantic layout items. Press/Pick selects and reveals a foreground object, refreshing the existing inspector. Shape custom actions provide text editing, directional movement, connection start and connection confirmation. Those actions and keyboard commands use the same canvas methods and accepted editor transaction path. An independent keyboard-focus identity draws a visible focus outline when the canvas is the first responder. Selection and focus notifications are posted, and rejected actions expose their reason in the status line and an accessibility announcement.

Keyboard behavior while the canvas owns first response:

- Option-Tab / Option-Shift-Tab enter and traverse visible foreground shapes and connectors in prepared paint order. Reaching either end leaves through the native key-view loop. If that loop has no other eligible control, the window takes first response.
- Tab / Shift-Tab leave the canvas immediately through the native key-view loop. Leaving cancels a pending connection; traversal never wraps into a focus trap.
- Arrows move selected shapes by one drawing unit; Shift uses ten. Option-arrows resize by the same steps.
- Return enters text editing for a single selected shape. Text editing uses the existing native `NSTextView` responder and undo/input session.
- C starts a connection from one selected unlocked shape. Traverse to another eligible shape and press Return to commit one connector transaction. Escape cancels without changing the drawing.
- Escape otherwise cancels transient canvas interaction and clears selection. Existing V/T/L tools remain canvas-local.

Movement clamps the selected root bounds together at page edges. Every affected group descendant is checked before a transform, using the shared `NativeEditProtection` policy. Group resizing also checks descendant position protection. A protected/guarded/unresolved property rejects the entire keyboard command, keeping the committed model unchanged; the same applies to protected text. Active previews and pending calculations reject new geometry/connection commands. Explicit inline text Escape/Command-Return restores canvas focus; ordinary field-resignation leaves the next native control in charge. The original native field-editor and inline text routing is retained: ordinary letters, marked-text input and text navigation do not route through canvas commands.

Integration hooks are `focusCanvasObject(_:)`, `traverseCanvasObjects(backward:)`, `transformKeyboardSelection(dx:dy:resize:)`, `editCanvasObjectText(_:)`, `startKeyboardConnection()` and `confirmKeyboardConnection()`. Existing menu/controller code can invoke these without altering their transaction ownership.

`CanvasAccessibilityTests` contains eight focused checks: composed-background provenance and same-UUID isolation, visibility/stable identity/group and endpoint relations/stale target refusal; live screen-frame conversion; native-window traversal and exit; native-window movement/resize with independent undo; protected descendant/text refusal without dirtying; locked grouped-connector refusal; native-window connection confirmation/undo/cancel; and inline text Escape/Command-Return restoring canvas command routing. All eight passed in the root's grouped run, `build/m2-native-features-focused-7.log`: **62 selected tests passed, zero failures, 3.908 seconds**. Earlier grouped6 exposed a real no-destination key-loop focus trap and two fixture assumptions: a zero-frame button was ineligible for keyboard focus, and AppKit constrained a requested window move at a screen edge. The retained final tests use eligible visible fields, check forward/backward exit and the no-destination fallback, and compare actual window movement.

The fixtures send synthetic `NSEvent`s through `NSWindow.sendEvent`; they do not establish physical input latency, real IME composition or actual VoiceOver navigation. Full application menu/ribbon/inspector/graph authoring, save/reopen, appearance variants and assistive-technology acceptance remain open until those journeys have retained evidence.

## Native QA follow-up

The actual running QA app exposed an editable selected layout item as disabled: the base `NSAccessibilityElement` availability default was not suitable for the semantic objects. Elements now explicitly report available/enabled when their prepared-scene object is visible and current. A locked foreground shape remains enabled for selection/inspection and exposes only those custom actions. Visible background content remains enabled for reading, with selection/focus actions excluded; hidden and stale elements are unavailable, disabled and cannot advertise selection actions. These decisions use the retained scene/runtime without evaluating formulas.

The focused suite is expanded to ten cases. In addition to availability assertions for editable, locked, background, hidden and removed objects, a native controller regression selects a shape to create the real inspector layout and sends Tab through the actual shape-search and inspector text controls, without assigning fixture key views. This detects key-loop problems hidden by a shared native field editor. The root owns automatic key-view-loop configuration in `EditorWindowController`. The explicit small-loop traversal fixture disables automatic loop rebuilding so AppKit honors its assigned destinations; the separate real-controller regression retains the application configuration and passed in grouped9. **All ten canvas tests passed** in `build/m2-native-features-focused-10.log`; that grouped run executed 95 tests with one failure in Find, so it is not an overall passing application result. The earlier eight-case result above remains historical evidence for that source version. The actual QA observation motivated the enabled-state fix; confirming the rebuilt app's accessibility tree and completing a real assistive-technology journey remain distinct follow-up evidence.
